# Decisions

Flat lookup of rulings, organized by domain. A short "not X" clause is allowed where the rejected alternative is tempting; longer rationale does not belong here. Rulings dated 2026-09-24 come from the kickoff session with the human.

## Form factor

Chrome extension, Manifest V3, loaded unpacked from `dist/`. Not a web app: only a content script can read Meet's speaker signals.
One full-tab app page (`app/app.html`) hosts recording, the library, settings and all processing. Not an offscreen document: the tab can show pickers, use WebGPU and be debugged. The tab warns on close while recording or processing.
The toolbar button is the primary control. One click on a tab opens the **start dialog** (`src/start/`) as an overlay at the top right of that page, over it and with no backdrop, with the tab it will record, a microphone selector, the save folder (changeable there) and one Start Capture button; the button again, or Escape, closes it and nothing records until Start. Not a start on the click itself: a click meant to see what Rescribe was doing started a recording while the previous one transcribed (2026-09-25, the human). Not a window of its own: it floated on the desktop, away from the page (2026-09-25, the human). The overlay is an iframe of the extension's page injected on the click's `activeTab` grant (`scripting`), not DOM built by a content script: the page's origin cannot hold the folder handle or the settings. A page that cannot host it (the browser's own pages, the Web Store, file:// without file access) gets the popup window, and in the overlay Change… brings the Rescribe tab forward, since Chrome refuses a picker to a frame inside another site's page. While recording, the badge shows `REC` and clicking the button opens the **stop dialog**, a small popup window (`src/stop/`) that asks what should happen to the recording: Save, one button per workflow (§ Workflows) and Discard; closing the dialog keeps recording. Not the app tab: the human is in the call and wants a decision, not a page (2026-09-25, the human). Not action popups (`action.default_popup`): Chrome opens one only from a click and closes it under a folder picker; popup-type windows can be opened when the call ends and host the pickers and the permission prompt.
A click leaves the human where they are, on a call platform tab (Meet; `src/lib/platform.ts` says which URLs count) or any other: the app tab opens, or stays, in the background; the dialogs and the badge are the feedback. It comes forward on its own only when a start needs the human: a microphone permission prompt (Chrome shows it only for a visible tab), a start that failed inside the app tab, a second Start while one is pending. A Start that cannot get the tab (`getMediaStreamId` refused) is answered in the dialog, not by a page. Not a stop: a click while recording opens the stop dialog wherever it lands and the app tab stays where it is (2026-09-24, the human: hitting record in Meet must not leave Meet; 2026-09-25: with the dialog there is no reason left to surface the app tab on any tab).
After a save in the stop dialog, a **processing tab** (`src/progress/`) opens in the browser window (the dialog stays until the export answers, then closes): it follows that recording's export and transcription to the end and can be closed at any time, since the app tab, pinned in the background, does the work. Not the app tab brought forward: closing it would stop the work. Not a badge: the toolbar shows nothing while a transcription runs; the tab is the feedback (2026-09-25, the human). A save from the app tab (Stop, a row) opens no tab: the row shows the progress.
While the app tab lives, a recording ends only by the human's decision (Save, Save with a workflow, Discard; Stop in the app tab is Save in one click) or by its stream dying. The Meet call ending (the adapter's `call-ended`) opens the stop dialog and keeps recording until the human answers, so a rejoin loses nothing. A stream that dies (Stop sharing, the captured tab closed) leaves the recording `stopped`: the dialog opens, the badge says `SAVE`, the row offers the same three choices, and nothing is exported or transcribed until one is taken. Not the automatic export of before: what becomes of a recording is the human's call, and Discard must be able to leave no trace (2026-09-25). A Save without a folder chosen picks one first (and makes it the Settings folder); it never ends as "recorded, not exported".
A recording interrupted by a crash or a closed app tab is the exception: recovered on the next open and exported to the Settings folder without asking (`recoverInterrupted`), because nobody was there to ask and the row's Save now and Delete cover the rest.
A recording waiting `stopped` never blocks a new one: the toolbar button on a call starts recording as if idle, and the waiting one keeps its row (and its dialog, from a click on the app tab). Not a gate: a missed call costs more than a decision postponed, the same ruling as for transcription (2026-09-25, adversarial review of #24).
A keyboard command (`toggle-recording`) mirrors the button.
Transcription never blocks recording: `query-status` answers the recorder's state, so Start Capture starts a new recording while the previous one transcribes and the pipeline queues it; the start dialog says what runs in the background. Not a lock: a missed call costs more than a later transcript.
Recording anything other than the current tab (a window, the whole screen) starts from the app tab, through Chrome's own picker.
The library's rows fold to one line, the title, when, how long, the status and the workflow run on it (2026-10-27, the human: the recordings took up too much space), and open on a click to everything else. Open without asking: the newest recording and one that is live or waits for the human; the human's own opening or closing holds for the tab's session (`sessionStorage`), and an action on a row counts as opening it, so its outcome stays in view when a newer recording arrives. Not a separate page per recording: the row is where its actions are.

## Capture

`getDisplayMedia` is the universal capture primitive for screen/window/tab from the app tab; `chrome.tabCapture` (no picker) is the one-click path from the toolbar button. Both produce the same `Source` and feed the same recorder.
The microphone is captured with `getUserMedia` in the app tab, independently of the display stream, and is optional per recording. Which one is a setting (`micDeviceId`), chosen in the start dialog and used on both paths; the default device when none is set or the chosen one is gone. Not a per-recording prompt: the choice is what the human picked last, shown before every Start.
Audio for the video file is mixed in the app tab with the Web Audio API; the mix exists only for playback. It is mono: the channels are speech, and a stereo mix doubled the video file's audio for nothing (2026-09-25, #27).
Video and audio are encoded by `MediaRecorder`. No WebCodecs, no ffmpeg in the browser.
The display is captured at 5 fps by default; Settings offers 10 and 30 (the recorder's bitrate cap follows). A call is faces and slides, and after the codec the frame rate is the largest lever on file size (a 58-minute call: 956 MB at 30 fps, 2026-09-25, #27). Not a lower resolution: text on a shared screen must stay legible. Capped at the source, not in the encoder: `MediaRecorder` encodes every frame it is given.

## Audio channels and speaker attribution

The microphone and the display audio are separate **channels**, kept apart all the way to the transcript. Each channel is transcribed on its own.
Speaker attribution is layered **evidence** resolved by one pure function (`src/lib/attribution.ts`). Every layer emits `SpeakerInterval`s in recording-relative seconds. Layers, in priority order: platform events (Meet/Teams DOM) > diarization model (later) > channel identity (mic = the human, display = "Speaker") > nothing.
The human's own platform tile is identified by evidence, not by its label: the participant whose speaking coincides with microphone speech (at least half of its speaking time, over at least five seconds; `src/lib/evidence.ts`) is the human, its intervals are not display evidence (the display channel never carries the human's voice) and it is listed under "my name"; exactly one tile may qualify (two that do, a colleague in the same room on their own laptop, are both kept); the label rule ("You") remains as the fallback for a tile that spoke too little to judge and for a recording without a microphone channel, where the leak of 2026-09-25 stands (DEFERRED § "Self tile without a microphone"). Not by Meet's label: Meet showed "You" on 2026-09-24 and the full name on 2026-09-25, when two thirds of the remote speaker's words in a 58-minute call were labelled as the human. Not by a DOM attribute of the self tile: none has been observed, and the microphone is ground truth on every platform.
With exactly one remote tile of substance, counted per tile (an unresolved name or a rejoin under a new id counts too) and only when the log holds a roster to vouch for who was there, the display channel's identity is that participant rather than "Speaker": everything the display carries is their voice, and Meet's indicator misses most of a listener's short replies while the human talks (181 of 304 remote segments in the call of 2026-09-25). With two or more, none known, or no roster line, the generic label stays; the Meet adapter re-sends the roster every 30 s so a recording started into a stable call holds one. A participant is a tile of substance: it spoke for the indicator's minimum duration, or was on screen for ten seconds of roster time (half the recording when that is shorter); Meet's flashes for a shared screen or a status ("You are presenting") are nobody.
Platform adapters are content scripts, one per platform, isolated in `src/content/`. They ship with a calibration mode because platform markup is obfuscated and changes.
On Meet, "speaking" is derived from the tile's audio meter _changing_ (class list flipped within 700 ms, `src/lib/activity.ts`), never from what a particular class means. Meet's level classes are opaque and renamed at will; motion is not.
Scraping Meet's live captions is not the default (it leans on Google's cloud speech recognition). It may become an opt-in adapter.
Model-based diarization of the display channel is a later layer, not v1. The evidence interface exists from day one so adding it is a new emitter, not a redesign.

## Speech recognition

Engine: NVIDIA Parakeet TDT 0.6B **v3** (multilingual, incl. Danish and English, word timestamps) via `parakeet.js`. Not Whisper: Parakeet is what FluidVoice runs and the quality the human already trusts.
Default runtime configuration: `backend: 'wasm'`, encoder int8, decoder int8, multithreaded (the extension is cross-origin isolated). Optional in Settings: `backend: 'webgpu'` with the fp32 external-data encoder. The single-file fp16 encoder is not offered: it does not fit the 32-bit WASM heap (the parakeet spike, 2026-09-24: ORT copies the 1.24 GB protobuf into the heap and parses a second copy; the fp32 export ships its weights as external data and fits).
The engine sits behind a small interface (`src/lib/asr/engine.ts`, planned) so sherpa-onnx or Whisper can be added without touching the pipeline.
Silence gating (VAD) runs before recognition on every channel. Energy-based first, Silero later.
The only permitted network traffic is the one-time model download from huggingface.co, cached in the browser. Never a CDN for runtime code: the ONNX WASM binaries ship inside `dist/vendor/ort/`.
No language setting. Parakeet v3 handles the language itself.
Transcription runs after the recording stops, in a Worker, not live. Live transcription is a later feature and the PCM already streams to disk, so it will be incremental, not a rewrite.
It starts by itself when a recording stops (Settings "Transcribe as soon as a recording stops", on by default); off, the library runs it. Recordings are transcribed one at a time, channels one after another; never two channels in the worker's queue at once, because a transcribe failure restarts the worker and fails whatever is queued behind it.

## Storage and output

During recording, data goes to the Origin Private File System (OPFS) through a worker with a sync access handle, appended as it arrives. Not straight to the user's folder: File System Access writes only commit on close.
On stop, the recording is exported to the folder the human chose in Settings (File System Access API, directory handle persisted in IndexedDB). Fallback if that API misbehaves in the extension origin: `chrome.downloads` into a subfolder of Downloads.
Output layout per recording, path template configurable in Settings, default `{date} {time} {title}/`: `recording.webm` (`recording.mp4` with the MP4 option), `transcript.md`, `transcript.json`, `meta.json`. The folder name and the header of `transcript.md` show the start in the machine's local zone at the moment each is written (the folder at Save, the header at transcription; a machine moved between zones in between shows them apart), through one formatter; the JSON files carry epoch milliseconds. Not UTC: the human reads the header next to the folder name (a header two hours off the folder, 2026-09-25). Not an offset suffix on the header: noise for every reader to cover a re-run on another continent.
Video container: WebM (AV1 + Opus; a keyframe every 10 s, 300 kbit/s video at 5 fps, 32 kbit/s audio) by default, MP4 (H.264 + AAC, a keyframe per second) as the option for players without WebM (QuickTime). Not MP4 by default (2026-09-25, #27, approved by the human): Chrome's MP4 muxer emits a chunk only at a keyframe, so the on-disk cadence costs a keyframe per second and a file five to ten times the size, while its WebM muxer emits a chunk per timeslice whatever the keyframe interval. Not VP9: AV1 at the same size is visibly better, and Chrome and Brave both record it (VP9 is the fallback, noted on the recording). Not WebCodecs with a fixed quantizer: faster, but worse than MediaRecorder's rate control at the same size.
The exported WebM gets the `Duration` element MediaRecorder leaves out, written into its header on export (`lib/webm.ts`, `export.ts` `exportVideoData`); a browser plays a WebM without one as an endless live stream. Its value is the PCM length, the monotonic clock the clusters follow, not the wall clock between start and stop (a machine asleep mid-recording advances one and not the other). Not a remux: an EBML edit of under a hundred bytes, and the OPFS copy stays as recorded.
There is one folder, the Settings one, and it is `~/.rescribe/recordings`, the one workflows read (§ Workflows). Save as… is gone (2026-10-23, the human: the dialog asks what should happen to a recording, not where it goes); a recording saved with it before keeps its own folder (the handle under IndexedDB `handles/export:<id>`, the name on the record as `exportRoot`), and Re-export goes there.
Transcript artifacts are written to OPFS first and exported second, and only into a directory the video already went to; a failed export leaves them in OPFS for **Save now**, which exports the video and the artifacts together. Not straight to the folder: transcription may finish long after Stop's click, when the folder's permission is gone (a restart) or no folder was ever chosen.
Settings live in `chrome.storage.local`. Recording metadata lives in IndexedDB. Media lives in OPFS until exported and, when the human says so, deleted. Deleting media removes the video and the PCM only; the transcript artifacts and the per-channel segments cache stay, so a transcript can still be exported and re-assembled. Not the whole directory: the audio is the expensive part, the transcript is what the human keeps.

## Workflows

A **workflow** is what the human can have done with a recording once its transcript is in the folder: a name, a line about it, a runner, a folder and the prompt Claude Code is given (2026-10-27, the human: after each recording "some standard thing with the transcript", packaged so it never has to be done by hand again). The stop dialog offers Save, Save with each workflow, and Discard; the row of a waiting recording offers Save, "Save and run workflow…" and Discard, and a transcribed row "Run workflow…", each opening a picker in its place (the workflows in a select, the chosen one's line, the button that does it, Cancel), on the one last run from a row. Not a button per workflow on the rows: they multiply (2026-10-27, the human). Until 2026-10-27 they were **routines**, code in this repository; the code and the record still call a workflow's run on a recording a routine (`Recording.routine`, `RoutineRun`, the host's `run-routine`), not renamed because records in IndexedDB carry the field. The first was **Index in Lawcel** (2026-10-23, the human): the transcript into lawcel-knowledge, the meeting's notes and the CRM, decisions and questions there, pushed, and since 2026-10-26 (the human) the call's action items as cards on the founders' board.
Workflows run outside the browser, through a **native messaging host** (`native/`, registered for the extension's id by `npm run install-host`). The extension lists, edits and deletes workflows through it, starts one on a recording and follows the run; it hands over the recording's id, title and directory, never its content. Not in the extension: it makes no network call and does no LLM work (PRODUCT § Non-goals); a workflow is the human's own tooling and may (each runs Claude Code). Not a folder watcher: the dialog needs the list and the row needs the outcome.
A workflow is the human's configuration, not code (2026-10-27, the human: changing a prompt must not take a PR; this reverses "a routine is code" of 2026-10-23): the host keeps it as files, `~/.rescribe/workflows/<id>/` (`workflow.json`: name, line, runner, folder; `prompt.md`), which the app's **Workflows** section lists, makes, edits and deletes through it, and which the human may also edit by hand (the app tab asks again when it comes back into view). Its id comes from its name when it is made and never changes, since records name it. A deleted one goes to `workflows/.trash/`. Not `chrome.storage`: the run reads the prompt outside the browser, and Brave and Chrome share one set. What is code is the **runner** (`runners/<id>/`: `runner.json`, an executable `run.sh`, `prompt.md`, the prompt a new workflow of it starts with, and `before.md`/`after.md`, what it puts around the workflow's prompt; `runners/README.md`), which changes by PR like any code and runs from the clone the host was installed from (each run from a copy taken at its start). Two runners: **Claude Code in a folder** (the prompt, in the workflow's folder, with the transcript to read, and a line back) and **Index in Lawcel** (below). Not a free-form script per workflow: the security below holds only for code that is reviewed.
The host makes the workflows directory on its first run, with a workflow of each runner that names a `seed`: Index in Lawcel, under its old id, so records that named the routine name the workflow. Never again after: a deleted one stays deleted.
A prompt names what it needs from the recording with `{{variables}}` of fixed names (`src/lib/routines.ts` `PROMPT_VARIABLES`: `title`, `date`, `time`, `participants`, `transcript`, `folder`, `workflow`), anywhere and as often as it likes. The host fills them in when a run starts and writes the prompt Claude Code gets, the runner's before, the workflow's, the runner's after, into the run's directory; the editor shows what the runner adds. Not a template language: a known name in double braces, anything else as written.
A workflow's folder is where its Claude Code reads and writes, so it is the most a call can reach (below). The host refuses, when a workflow is saved and again when a run starts (a hand edit), a folder not inside the home folder, the home folder itself, a hidden folder at its top (keys, settings, programs on the PATH), `~/Library` but for iCloud Drive and the cloud drives (`Mobile Documents`, `CloudStorage`), and one that holds or is inside Rescribe's own (`~/.rescribe`, the clone with the runners) (`native/workflows.ts` `checkFolder`). Not any folder: a call could otherwise have the agent write a launch agent, a runner's script or another workflow's prompt. A folder of code the human runs stays the human's risk to take; the editor says so.
The host reads recordings from one folder, `~/.rescribe/recordings`, by the export path under it. It checks that the Settings folder carries that folder's name, that the directory is inside it, and that its `meta.json` names the recording. Not a path from the extension: a folder handle has none. A run reads copies of the transcript, `transcript.json` and `meta.json` in its own directory (`recording/`), never the recording's folder, which stays the archive.
A workflow starts only when its recording is `done` with the transcript in the folder, and at most once per pick: each start names itself (`runKey`), and the host answers a name it has seen with that run. A start the host did not answer in time stays waiting and is asked again. Not "failed, try again": the run may be going, and a second one would push the meeting twice. Chosen at the save, it makes the transcription run whatever Settings say. It runs detached from the browser (a supervisor in a session of its own, `native/supervise.ts`), so closing the tab or quitting the browser does not stop it. The human learns the outcome from a macOS notification and from the record, which the app tab polls while a run goes on.
A run never spends the human's API keys: its environment has no `ANTHROPIC_API_KEY`, so `claude` bills the subscription.
What was said on a call is untrusted input: anyone on it can address the agent that reads it. A runner runs Claude Code `--restricted --strict-mcp-config --tools Read,Write,Edit,Glob,Grep` (no shell, no web, no messages to other sessions, no MCP servers, no user settings; file tools confined to its working directory and the run's copies of the recording, `--add-dir`; no writes to git or settings files without a person's approval, which a headless run never gets) with the prompt the host filled in, never with permissions bypassed (`native/runners.test.ts`), and does what needs a shell or the network (git, gh) in its own script. Not `bypassPermissions`: the first version had it, and the adversarial review showed a sentence on a call could have the agent read `.env` keys into a file it pushes, or send mail (2026-10-23). The before and after of Claude Code in a folder say that the transcript is material, never instructions.
Index in Lawcel's runner stages the transcript and `meta.json` in a git worktree of the workflow's folder, the lawcel-knowledge clone, inside the run's directory. Claude Code writes the note and the CRM, decisions, questions and reminders there, and hands back the name; `run.sh` files the transcript under it, commits, rebases and pushes `HEAD:main`, and is done only once the commit is on `origin/main`, or when a meeting indexed again leaves nothing to commit. Not in the human's clone, which may be mid-edit; that clone is fast-forwarded afterwards when it can be. It copies the transcript and leaves the recording folder whole. Not a move: the folder is the archive Re-export and a re-run work from.
Index in Lawcel puts the call's action items on the founders' board (`https://github.com/orgs/Lawcel/projects/2`) as issues in lawcel-knowledge, which the board adds in Triage on its own (2026-10-26, the human; until then the routine filed none, the board being for the founders' Monday review, which still triages what it files). The agent writes each card as files (`.rescribe/cards/<n>/`: `title`, `body.md`, `assignees`). `run.sh` reads the board (one issue to a line or two, so the agent's Read takes it whatever its size) and who can be assigned before the agent starts, so the agent can leave out what the board has; bounds the cards without ever holding back the notes (at most ten or none; a title of one line and 120 characters, a body of 2000; HTML, code fences and mentions made inert; an assignee who cannot be assigned there left out; a card without a title or body, or anything out of place in the hand-over, named in the summary); and files them with `gh` once the note they link to is on `origin/main`, after reading the board again and leaving out a card whose title is open there or already filed from the same call (a failed run's, an overlapping run's, the meeting indexed again), whatever the agent made of it, each ending in a line it writes itself: the meeting's note, and that an agent filed it. A card is assigned only to an owner named on the call, which overrides lawcel-knowledge's no-assignee default for those. Not the agent filing them: it has no shell and no network (above). The repository is the one origin's push URL names, git's rewrites applied and an SSH alias resolved, as `gh repo view` reads it, not a constant: the cards go where the notes go, a workflow pointed at another clone must not file on the founders' board, and one gh cannot place stops the run. Not a refusal of the whole run over one card: a card's problem is the board's, and the call's notes are worth pushing regardless. A card left out as already on the board is named in the summary, so a call's item that matched an older card stays in view. Not items made through the project's API: the local token has no `project` scope, and an issue reaches the board without one.

## Stack

TypeScript, strict. Vanilla DOM, no UI framework, no CSS framework. Not React.
esbuild bundles `src/` into `dist/`; `tsc --noEmit` type-checks; no other build tooling. Imports between source files use the `.ts` extension so Node can run tests without a build.
Dependencies are npm packages bundled by esbuild. Runtime assets that cannot be bundled (WASM) are copied into `dist/vendor/` by the build script.
Prettier formats; `.prettierrc` is the source of truth.

## Testing

Pure logic (attribution, transcript assembly, VAD, path templates) is unit-tested with Node's built-in test runner, tests colocated as `*.test.ts`.
The record-to-transcript path is end-to-end tested with Playwright driving the real extension in Chromium with fake media devices (`e2e/`).
What fake devices cannot exercise (a real Meet call, the real folder picker, QuickTime playback) is a [[LIVE_CHECKS]] entry the human runs.
The native host is tested as the browser drives it, a process per framed message (`native/host.test.ts`: the workflows made, edited, refused and deleted, and runs), and through the test browser in e2e with a runner of the harness's own (`e2e/routines.spec.ts`, the Workflows section included). Each runner's `run.sh` runs against a stand-in for `claude`: Claude Code in a folder in `native/runners.test.ts`, Index in Lawcel in `native/index-in-lawcel.test.ts` against a local origin and a stand-in for `gh` too (which runs the script's jq programs with `jq`; the file is skipped without it). A real workflow's run (Index in Lawcel pushes to a shared repository) is a [[LIVE_CHECKS]] entry.

## Process and tracking

Full lawcel cycle: worktree per change (`git gtr`), PR, self-test, adversarial review for pipeline diffs, mistakes ledger, merge by the agent.
GitHub Issues on `ulfaslak/rescribe` track dev work. Claim comment `🔨 Started work on this.` marks in-progress. Labels: `bug`, `enhancement`, `eventually`.
Release is manual: build `main` in the primary clone, reload the extension in Chrome.

## Naming

The product and repo are "Rescribe". The human's own speaker label defaults to "Me" and is a setting.
Transcription progress speaks in the human's terms: the job is steps, named in every view as the speech model, the microphone as the human (by the name from Settings), the call, who said what and the transcript files, with one bar for the whole job. Not channel ids, region counts or a bar per channel: a bar that filled once per channel read as the same job run twice (2026-09-25, #31, the human).
What the human has done with a recording after it is saved is a **workflow** in every page (2026-10-27, the human); "routine" is left only in the code and on the record (§ Workflows), and a runner appears only in the Workflows section, as what a workflow "runs with".
